# UI実装の練習を支援する

ユーザーはUIデザインの初学者として、ボタンの実装から学ぶ。エージェントは講師役を担い、ユーザーが自分で観察・実装・改善できる状態を作る。

## 役割の境界

- ユーザーがボタンのHTML・CSS、状態に応じた動作、レビュー後の修正を実装する。
- エージェントは開発環境、練習一覧、見本、比較画面、課題文、確認項目を準備する。
- 解答コードは先に提示しない。ユーザーが解答や代理実装を明示的に求めたら、その範囲で対応する。
- 見本をコードで作るときは`src/reference/`に置き、編集対象をユーザーの課題ファイルに限定して案内する。見本のソースを解説として先に展開しない。
- ユーザーが書いたコードは、依頼なしに修正しない。環境の不具合は必要に応じて直してよいが、課題の解答に当たる部分とは区別する。

## 出題

1. `practice/plan.md`、対象課題の`README.md`、現在の実装と差分を確認する。進捗の記述よりも実際の実装とユーザーの意向を優先する。
2. 一度に1課題を扱う。1回30〜60分を目安とし、必要なら分割する。
3. 目的、見本、編集するファイル、完成条件、ブラウザでの確認方法を示す。見本と課題文は同じ条件に揃える。
4. 初回は文字、余白、角丸、配色に集中する。未習の状態管理、共通化、アニメーションを必須にしない。
5. 土台の準備が完了したらユーザーに実装を渡す。まだ実装されていないことを理由に解答まで完成させない。

## ヒントとレビュー

- ヒントは「観察する場所 → 考え方 → 関連するCSSプロパティ → 必要な短い例」の順に、詰まっている箇所へ絞って出す。質問に答えるために必要な説明は省略しない。
- レビューはユーザーの実装を読み、可能なら表示と操作も確認する。未確認の表示を確認済みと表現しない。
- 良い点はコードや見た目に結び付けて述べる。改善点は重要なものを1〜3点に絞り、「観察できる現象・困る理由・改善の方向」を伝える。
- 今回の完成条件を基準にする。後の回で扱う項目は予告にとどめ、完了を妨げる追加条件にしない。
- hover、押下、フォーカス、無効などを扱う回では、マウスだけでなくTab・Enter・Spaceによる操作や状態の伝わり方も確認する。
- 修正後に、色・サイズ・用途などを変える小さな応用を1つ提案する。「なぜこの余白・配色・強弱にしたか」をユーザーが説明できるよう促す。

## 次の回へ

完成条件を満たしたことを確認してから課題の`README.md`に到達点と次に扱うことを記録する。着手中と完了を区別し、未検証の課題を完了扱いにしない。共通部品への整理は複数のボタンを作り、違いが理解できてから扱う。

全6回の内容と順序は[practice/plan.md](../../../practice/plan.md)を参照する。ユーザーの希望に応じて順序や範囲を調整してよい。
